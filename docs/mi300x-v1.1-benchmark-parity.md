# MI300X benchmark parity with GPU Benchmarks v1.1

The CDNA3 runners below use the device implementations from [GPU Benchmarks
v1.1](https://github.com/sarchlab/gpu_benchmarks/tree/a8ca84f8ce4373b3c091d4dc97a8f067607847a9)
and the ROCm 10.2.0 compiler used for the MI300X reference collection. They use the
collection's inputs, per-pass launch order, thread and block shapes, and output
checks. See [the gfx942 build instructions](gfx942-kernel-build.md) to rebuild the
embedded code objects.

The D2D memory-bandwidth runner follows the ROCclr `__amd_rocclr_copyBuffer` launch,
using the [ROCm Systems revision in the ROCm 10.2.0 distribution](https://github.com/ROCm/rocm-systems/tree/43fa692e568e65a1fb84f2d1c74415b042839f10).
Its aligned copy uses 16 bytes per work-item, 512 work-items per group and at most
304 groups for the collected MI300X cases. It covers the measured aligned D2D
copies. The copied bytes are checked against the source. The shared-memory
benchmark uses generic FLAT instructions with all active lanes targeting LDS,
which is the LDS aperture case supported in the CDNA3 timing model.

The measured Tier 2 kernel bodies match the archived HIP translation units with
the same compiler for 31 workloads. AES, CFD and CutCP have relative offsets that
differ because of linked read-only data placement. The kernels still read the
archived AES S-box, CFD far-field coefficients or CutCP neighbor offsets. The
profiler rounds fixed LDS allocation up to 512-byte units on gfx942, while the
simulator packet retains the exact byte count including any requested dynamic LDS.

The list excludes workloads with no corresponding runner and entries using a
different benchmark algorithm from another suite. PolyBench Gram–Schmidt and
NPB EP use global floating-point atomic adds in the hardware collection and
remain tracked in [MGPUSim #278](https://github.com/sarchlab/mgpusim/issues/278).

## Reproduce representative recorded cases

The case numbers identify configurations in the GPU Benchmarks v1.1 MI300X
collection. Run the sample and arguments from the table using the shared flags.
Add `-timing` for the MI300X timing model.

```sh
go run ./amd/samples/empty_kernel -arch=cdna3 -gpu=mi300x -verify -disable-rtm \
  -num-blocks=1 -block-size=32
```

The matched launch sequences cover the benchmark kernels for one workload pass.
The hardware collection's cache warm-up and repeated profiling passes are part
of its measurement harness. Timing calibration against the collected data is a
separate step. The checked-in calibration CSV describes an earlier collection.
The case parameters below correspond to v1.1.

## Runners without a v1.1 collection case

| Benchmark | Source | Sample and arguments |
|---|---|---|
| `code_fetch_latency` | [GPU Benchmarks #198](https://github.com/sarchlab/gpu_benchmarks/pull/198) | `code_fetch_latency -body-ops=256 -loops=1 -num-blocks=1 -threads-per-block=64` |

`code_fetch_latency` was added to GPU Benchmarks after v1.1. The v1.1 collection
has no case for it, and the release calibration has no hardware reference data
for it.

Kernels with 16384 body operations or more close their loop with
`s_setpc_b64`, which the CDNA3 emulator does not implement. They run with
`-loops=1` only.
