# Phase 2 Research: ML Workloads — GPU Kernel Analysis for MGPUSim

## 1. Introduction & Motivation

Modern machine learning inference and training workloads are dominated by
transformer-based models — GPT-2/3/4, Llama-2/3, Mistral, and their
derivatives. These models consume the majority of GPU compute cycles in
production data centers, yet traditional GPU benchmark suites (Rodinia,
Parboil, PolyBench) were designed for scientific computing and provide
almost no coverage of ML-specific kernel patterns.

This document analyzes the GPU kernels generated by PyTorch and vLLM,
examines how to profile and extract individual kernels for benchmarking,
assesses current MGPUSim coverage, identifies gaps, and recommends a
concrete approach for Phase 2 simulation of representative ML workloads.

### 1.1 Why This Matters for MGPUSim

GPU architecture simulators like MGPUSim require:

1. **Open-source kernels** — vendor libraries (cuBLAS, cuDNN, rocBLAS)
   are closed-source binaries that cannot be disassembled or simulated
2. **Isolated kernel execution** — end-to-end ML pipelines are too
   complex for cycle-level simulation
3. **Configurable problem sizes** — to sweep across architectural
   design points and model scales
4. **Representative compute and memory patterns** — matching the
   instruction mix and memory hierarchy stress of real workloads

### 1.2 Scope

This analysis covers the full pipeline from ML framework execution to
individual GPU kernel identification, with specific focus on:
- PyTorch eager mode, `torch.compile`, and TorchInductor code generation
- vLLM inference serving and PagedAttention
- Flash Attention memory-efficient implementation
- Kernel profiling and extraction techniques
- Mapping to existing and planned MGPUSim benchmarks

## 2. PyTorch GPU Execution Model

### 2.1 Execution Modes

PyTorch provides three GPU execution paths, each producing different
kernel dispatch patterns:

| Mode | Mechanism | Kernel Generation | Fusion |
|------|-----------|-------------------|--------|
| Eager mode | Op-by-op dispatch | ATen library kernels + cuBLAS/rocBLAS | None |
| `torch.jit.trace/script` | TorchScript IR | Same kernels, reordered | Limited |
| `torch.compile` | TorchInductor + Triton | Triton-generated fused kernels | Aggressive |

**Eager mode** dispatches each PyTorch operation to a pre-compiled CUDA/HIP
kernel via the ATen dispatcher. GEMM operations route to cuBLAS/rocBLAS;
elementwise operations use ATen's own kernels. Each operation launches a
separate kernel, incurring launch overhead and requiring intermediate
results to round-trip through global memory.

**torch.compile (PyTorch 2.0+)** traces the computation graph, applies
TorchDynamo for graph capture, and feeds it to TorchInductor, which
generates Triton kernels for elementwise/reduction operations and
delegates GEMM to cuBLAS/rocBLAS. The key benefit is **kernel fusion**:
multiple elementwise operations are combined into single kernels.

### 2.2 TorchInductor and Triton Code Generation

TorchInductor's pipeline: Python → TorchDynamo (graph capture) →
FX Graph → TorchInductor (fusion/scheduling) → Triton kernels
(elementwise/reduction) + rocBLAS calls (GEMM) → AMDGPU IR → HSACO.

Triton generates highly specialized GPU code per problem size. For
simulation purposes, the Triton-generated kernels are fragile (they
change across versions and auto-tune for specific hardware), so
hand-written kernels with explicit parameters are preferred for
reproducible architecture research.

### 2.3 Kernel Dispatch in a Transformer Forward Pass

A single transformer layer in eager mode dispatches approximately:

| Step | Operation | Kernel(s) Dispatched |
|------|-----------|---------------------|
| 1 | RMSNorm / LayerNorm | `layer_norm_forward_kernel` or `rmsnorm_kernel` |
| 2 | QKV linear projection | `rocblas_sgemm` (3× or fused) |
| 3 | RoPE positional encoding | `rotary_embedding_kernel` (elementwise) |
| 4 | Attention score (Q·K^T) | `rocblas_sgemm_batched` |
| 5 | Softmax | `softmax_warp_forward` |
| 6 | Attention output (Attn·V) | `rocblas_sgemm_batched` |
| 7 | Output projection | `rocblas_sgemm` |
| 8 | Residual add | `elementwise_add_kernel` |
| 9 | RMSNorm / LayerNorm | `layer_norm_forward_kernel` |
| 10 | Gate projection (SwiGLU) | `rocblas_sgemm` |
| 11 | Up projection | `rocblas_sgemm` |
| 12 | SiLU activation + gate | `silu_mul_kernel` (fused or 2 kernels) |
| 13 | Down projection | `rocblas_sgemm` |
| 14 | Residual add | `elementwise_add_kernel` |

With `torch.compile`, steps 1+2, 8+9, and 10+11+12 can be partially
fused, reducing total kernel launches from ~14 to ~8-10.

## 3. Key ML Kernel Categories

### 3.1 Kernel Time Breakdown

Profiling a Llama-2-7B forward pass reveals the following GPU time
distribution:

| Category | Training (% GPU time) | Inference (% GPU time) | Bound |
|----------|----------------------|------------------------|-------|
| GEMM (linear projections) | 55–75% | 40–60% | Compute |
| Attention (Q·K^T + softmax + Attn·V) | 10–20% | 15–30% | Varies |
| Normalization (LayerNorm/RMSNorm) | 3–8% | 3–5% | Memory |
| Activations (GELU, SiLU, SwiGLU) | 3–6% | 2–4% | Memory |
| Positional encoding (RoPE) | 2–5% | 2–5% | Memory |
| Other (embedding, residual, sampling) | 2–5% | 5–10% | Memory |

### 3.2 Arithmetic Intensity Analysis

The compute-memory balance point on MI300a (peak 47.9 TFLOPS FP32,
5.3 TB/s HBM) is approximately AI ≈ 9.0 FLOP/byte. Kernels below
this threshold are memory-bandwidth-limited:

| Kernel | Arithmetic Intensity (FLOP/byte) | Classification |
|--------|----------------------------------|----------------|
| GEMM (K=4096) | ~2048 | Compute-bound |
| Attention (seq=4096) | ~2048 | Compute-bound |
| Softmax | 0.4–0.6 | Memory-bound |
| LayerNorm | 0.8 | Memory-bound |
| RMSNorm | 0.75 | Memory-bound |
| RoPE | 1.0 | Memory-bound |
| GELU / SiLU | 1.5 | Memory-bound |
| Fused SwiGLU | 0.33 | Memory-bound |

This bifurcation is critical: GEMM accuracy depends on compute unit
modeling, while all other kernels depend on memory subsystem accuracy.

## 4. vLLM and Inference-Specific Kernels

### 4.1 vLLM Architecture

vLLM is the dominant open-source LLM serving engine, introducing
**PagedAttention** for efficient KV cache management. Its GPU kernel
profile differs substantially from training:

- **Prefill phase**: processes the full input prompt; kernel profile
  resembles training (GEMM-dominated, large batch sizes)
- **Decode phase**: generates one token at a time; small effective
  batch size makes GEMM memory-bound and elevates attention cost

### 4.2 PagedAttention

PagedAttention manages the KV cache using virtual memory concepts:

1. KV cache is divided into fixed-size **blocks** (e.g., 16 tokens)
2. A **block table** maps logical sequence positions to physical
   GPU memory blocks (analogous to OS page tables)
3. The attention kernel uses indirect addressing to gather KV vectors
   from non-contiguous physical blocks

At the GPU kernel level, PagedAttention generates:
- **Indirect memory loads**: gather operations through block table
- **Variable-length attention**: different sequences have different
  lengths, requiring masking logic
- **Block-level parallelism**: each CUDA/HIP block processes one
  query head against all KV blocks for one sequence

This access pattern is fundamentally different from standard dense
attention and stresses the memory subsystem with irregular access.

### 4.3 Flash Attention

Flash Attention (Dao et al., 2022) avoids materializing the full
N×N attention matrix by tiling the computation:

1. Load a block of Q (B_r rows)
2. For each block of K, V (B_c columns):
   a. Compute block attention scores: S_block = Q_block · K_block^T
   b. Update running softmax statistics (online softmax)
   c. Accumulate weighted V: O += softmax(S_block) · V_block
3. Write final output O (never materializing full S matrix)

Memory complexity drops from O(N²) to O(N), enabling sequence lengths
of 32K+ that would otherwise exceed GPU memory. Flash Attention 2
improves parallelism by splitting across the sequence dimension and
reducing non-matmul FLOPs, achieving 50–73% of A100 peak throughput.

### 4.4 Quantization Kernels

Production inference increasingly uses quantized models (INT8/W8A8 via
SmoothQuant, INT4/W4A16 via GPTQ/AWQ, FP8/E4M3 native on CDNA3).
These introduce integer multiply-accumulate and mixed-precision
conversion instructions not present in standard FP32 benchmarks.
Currently outside MGPUSim's instruction support.

## 5. Kernel Profiling and Extraction Methods

### 5.1 PyTorch Profiler

`torch.profiler` captures per-kernel GPU time, launch configuration,
and input shapes. Use `prof.key_averages().table(sort_by="cuda_time_total")`
to identify the top-N kernels by GPU time contribution.

### 5.2 ROCm Profiler (rocprof)

For AMD GPUs, `rocprof --stats --hsa-trace` collects hardware counters:
`SQ_WAVES` (wavefronts), `SQ_INSTS_VALU` (compute intensity),
`SQ_INSTS_LDS` (shared memory usage), and `TCC_HIT/TCC_MISS` (L2 cache).

### 5.3 Extracting Standalone Kernels

To isolate ML kernels for simulation: (1) profile the full model to
identify top-N kernels, (2) record input/output tensor shapes, (3)
implement standalone CUDA/HIP kernels matching the compute pattern,
(4) validate against in-framework timing, (5) compile for GCN3/CDNA3.
The `workloads/ml_kernels/` suite follows this methodology with 7
kernels covering the top operations by GPU time.

## 7. Gap Analysis

### 7.1 Missing Kernel Types

| ML Kernel | Priority | Reason for Gap |
|-----------|----------|---------------|
| PagedAttention | High | Non-standard memory access (indirect gather via block table) |
| Flash Attention (tiled) | High | Complex tiling with online softmax; requires LDS support |
| Quantized GEMM (INT8) | Medium | Requires INT8 multiply-accumulate instructions |
| Mixed-precision GEMM (FP16) | Medium | MFMA FP16 instructions not implemented |
| BF16 operations | Medium | No BF16 instruction support in MGPUSim |
| FP8 GEMM (E4M3) | Low | CDNA3-specific; very new |
| Grouped-Query Attention | Medium | Variant of attention with different Q/KV head counts |
| MoE routing (top-k gating) | Low | Permutation + selection; sparse pattern |

### 7.2 Simulator Limitations

| Limitation | Impact | Workaround |
|------------|--------|------------|
| No MFMA instruction support | Cannot simulate Tensor/Matrix Core GEMM | Use V_FMA_F32 tiled GEMM |
| No AGPR (accumulation registers) | MFMA outputs unavailable | N/A — tied to MFMA |
| Partial FP16 support | Cannot benchmark half-precision kernels | Focus on FP32 |
| Simulation time O(N³) for GEMM | Llama-scale shapes impractical | Use GPT-2 sizes |
| No INT8/BF16 instructions | Cannot benchmark quantized inference | Future work |
| LDS banking accuracy untested | Tiled GEMM accuracy may suffer | Validate with small sizes |

### 7.3 Practical Simulation Boundaries

Based on measured simulation times for `matrixmultiplication`:

| Matrix Size | Est. Sim Time | ML Model Equivalent |
|-------------|---------------|-------------------|
| 256×256 | ~15 sec | Below any real model layer |
| 512×512 | ~2 min | — |
| 768×768 | ~5 min | GPT-2-Small (hidden dim) |
| 1024×1024 | ~15 min | GPT-2-Medium (hidden dim) |
| 4096×4096 | >1 hour | Llama-2-7B (hidden dim) |

GPT-2-Small shapes (768–3072 dimensions) are the practical upper
bound for GEMM simulation sweeps. Memory-bound kernels (softmax,
layernorm, RoPE, activation) simulate faster and can handle larger sizes.

## 8. Simulation Feasibility

### 8.1 Feasible Now (V_FMA_F32 Based)

The following ML kernels can be simulated in MGPUSim today using
standard FP32 instructions, without any simulator modifications:

1. **Tiled GEMM** — shared-memory tiling with V_FMA_F32 accumulation
2. **Softmax** — row-wise max/subtract/exp/sum reduction
3. **LayerNorm / RMSNorm** — mean/variance reduction + normalization
4. **RoPE** — elementwise sin/cos with register arithmetic
5. **GELU / SiLU activation** — elementwise transcendental functions
6. **Fused SwiGLU** — fused elementwise (2 reads, 1 write, SiLU + mul)
7. **Naive attention** — batched GEMM + softmax composition

These cover the core compute patterns of transformer models. Absolute
throughput will differ from MFMA-accelerated production kernels, but
**relative scaling behavior** (how performance changes with problem
size, tile size, and CU count) is preserved — which is the primary
metric for architecture studies.

### 8.2 Requires Simulator Extension

| Kernel | Required Extension | Effort |
|--------|-------------------|--------|
| Flash Attention (tiled) | Robust LDS support + complex control flow | Medium |
| PagedAttention | Indirect memory addressing patterns | Medium |
| FP16 GEMM | V_PK_FMA_F16 (partial support exists) | Medium |
| INT8 GEMM | V_MUL_I32_I24 or similar | Medium |
| MFMA GEMM | V_MFMA_F32_* instruction family + AGPRs | High |

### 8.3 Accuracy Expectations

Expected MAPE vs MI300a: tiled GEMM 15–22% (baseline: 22% for naive),
memory-bound kernels (softmax, layernorm, activation) 15–25%,
attention composition 20–30%. Memory-bound kernel accuracy depends
primarily on the cache and bandwidth model fidelity.

## 9. Recommended Approach for Phase 2

### 9.1 Priority Ordering

**Tier 1 — Integrate existing ml_kernels into MGPUSim** (highest value):
1. Port `workloads/ml_kernels/gemm` → `amd/samples/gemm` (tiled GEMM)
2. Port `workloads/ml_kernels/softmax` → `amd/samples/softmax`
3. Port `workloads/ml_kernels/layernorm` → `amd/samples/layernorm`

**Tier 2 — Add remaining kernels**:
4. Port `activation`, `rope`, `fused_swiglu`, `attention`
5. Validate all against MI300a hardware measurements

**Tier 3 — Extend coverage** (requires simulator work):
6. Implement Flash Attention (tiled attention with online softmax)
7. Implement PagedAttention (indirect KV cache access)
8. Add FP16 GEMM support

### 9.2 Benchmarking Strategy

For each ported kernel:

1. **Compile for GCN3/CDNA3** using the MGPUSim benchmark framework
2. **Run simulation sweeps** across problem sizes from `params.json`
3. **Collect hardware baselines** on MI300a using `rocprof`
4. **Compute MAPE** for each kernel × size combination
5. **Analyze scaling trends** — does sim track hardware as size varies?

Focus on GPT-2-Small shapes first (768–3072 dimensions) where
simulation is practical, then selectively validate at Llama-2-7B
shapes (4096+) for the most critical operations.

### 9.3 Success Criteria

- **Coverage**: ≥5 ML kernel types simulable in MGPUSim
- **Accuracy**: <25% MAPE for tiled GEMM (improvement over 22% naive)
- **Scaling fidelity**: sim and hardware show same trends vs problem size
- **Parameterization**: configurable dimensions matching real model shapes
